# QSRegistry — 脚本节点设计

> 返回 [总览](QSGraphDB设计.md)

## 1. 背景与动机

### 1.1 现有重建机制的局限

当前 QSGraphDB 从图库恢复因子对象采用**元数据重建**方式：将因子的类路径、参数 JSON、算子引用、依赖关系等元数据存入图节点，重建时通过 `importlib` 重新导入类并反序列化参数。这种方式存在以下风险：

- **类重构脆弱**：类名或模块路径变更后，已入库的因子无法重建
- **隐式状态丢失**：因子创建时的某些运行时状态（如闭包、动态生成的函数）难以完整序列化
- **不可审计**：图中只记录了重建所需的最小元数据，无法追溯因子的原始定义逻辑
- **不可自愈**：源文件丢失后，即使图中有完整元数据，也无法重建因子

### 1.2 设计目标

引入**脚本节点**（`脚本`），将因子的定义脚本作为一等公民纳入计算图：

1. **脚本即源码**：将 `.py` 脚本内容直接存入图节点，实现源码级容灾
2. **依赖可图查**：脚本间依赖（`FactorDeps`）建模为图关系，支持拓扑查询和影响分析
3. **重建可选路径**：提供"脚本重建"模式，通过重跑 `defFactor(fdi)` 恢复因子对象
4. **生产链路完整**：打通 `因子表 ← 因子存储器 ← 因子 ← 脚本 ← 依赖脚本` 全链路

## 2. 节点设计

### 2.1 脚本节点 (`脚本`)

表示一个因子/策略定义脚本文件。

| 属性 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `QSID` | string | 是 | **唯一标识**，`sha256(Content)` 前 16 位，内容相同则 QSID 相同 |
| `Name` | string | 是 | 脚本文件名（如 `momentum.py`） |
| `Path` | string | 否 | 原始文件路径（可能为空或失效，仅供参考） |
| `Content` | string | 是 | 脚本完整源码 |
| `ContentHash` | string | 是 | `sha256(Content)` 完整哈希，用于快速比对变更 |
| `EntryFunction` | string | 是 | 入口函数名：`defFactor` 或 `defStrategy` |
| `ModuleType` | string | 是 | 模块类型：`FactorDef` / `StrategyDef` |
| `MetaJSON` | string | 否 | JSON 编码的 `__FACTOR_META__` 或 `__STRATEGY_META__` 完整内容 |
| `Author` | string | 否 | 作者 |
| `Description` | string | 否 | 脚本描述 |
| `Tags` | list[string] | 否 | 检索标签 |
| `Embedding` | list[float] | 否 | 脚本描述文本的嵌入向量 |
| `EmbeddingModel` | string | 否 | 嵌入模型名称 |
| `EmbeddingDim` | int | 否 | 嵌入维度 |
| `CreatedAt` | datetime | 是 | 首次注册时间 |
| `UpdatedAt` | datetime | 是 | 最后更新时间 |

**QSID 设计说明**：采用内容哈希而非路径哈希，确保：
- 同一内容的脚本（复制/移动后）不会产生重复节点
- 内容变更后 QSID 变更，触发下游关系更新
- 可通过 `ContentHash` 快速判断脚本是否已入库且未变更

### 2.2 因子节点扩展

在现有 `因子` 节点上增加一个可选属性：

| 属性 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `DefScriptQSID` | string | 否 | 定义该因子的脚本节点 QSID（仅 FactorDef/StrategyDef 来源的因子） |

该属性通过 `定义于` 关系关联到脚本节点，同时冗余存储在属性上以支持直接查询。

### 2.3 策略节点扩展

在现有 `策略` 节点上增加：

| 属性 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `DefScriptQSID` | string | 否 | 定义该策略的脚本节点 QSID |

## 3. 关系设计

### 3.1 新增关系

```
因子    -[:`定义于`]-> 脚本    # 因子由该脚本定义
策略    -[:`定义于`]-> 脚本    # 策略由该脚本定义
脚本    -[:`依赖脚本`]-> 脚本  # 脚本间的模块依赖（FactorDeps/StrategyDeps）
脚本    -[:`使用因子库`]-> 因子库  # 脚本声明的 DBDeps
脚本    -[:`打标签`]-> 标签    # 脚本标签
```

### 3.2 关系属性

| 关系 | 方向 | 属性 | 语义 |
|------|------|------|------|
| `定义于` | 因子 → 脚本 | 无 | 因子由该脚本的 `defFactor`/`defStrategy` 产出 |
| `定义于` | 策略 → 脚本 | 无 | 策略由该脚本的 `defStrategy` 产出 |
| `依赖脚本` | 脚本 → 脚本 | `FactorNames: list[string]` | 依赖的因子名列表（来自 `FactorDeps`） |
| `使用因子库` | 脚本 → 因子库 | `Purpose: string` | 用途说明（来自 `DBDeps`） |
| `打标签` | 脚本 → 标签 | 无 | 复用现有标签机制 |

### 3.3 约束与索引

```cypher
-- 唯一性约束
CREATE CONSTRAINT script_qsid IF NOT EXISTS
    FOR (s:`脚本`) REQUIRE s.QSID IS UNIQUE;

-- 查询索引
CREATE INDEX script_name IF NOT EXISTS FOR (s:`脚本`) ON (s.Name);
CREATE INDEX script_module_type IF NOT EXISTS FOR (s:`脚本`) ON (s.ModuleType);
CREATE INDEX script_entry IF NOT EXISTS FOR (s:`脚本`) ON (s.EntryFunction);
CREATE INDEX factor_def_script IF NOT EXISTS FOR (f:`因子`) ON (f.DefScriptQSID);
CREATE INDEX strategy_def_script IF NOT EXISTS FOR (s:`策略`) ON (s.DefScriptQSID);

-- 向量索引（复用已有模型维度）
CREATE VECTOR INDEX script_embedding IF NOT EXISTS
    FOR (s:`脚本`) ON (s.Embedding)
    OPTIONS {indexConfig: {`vector.dimensions`: 1024, `vector.similarity_function`: 'cosine'}};
```

## 4. 完整图结构

### 4.1 全链路示例

以一个典型的 FactorDef 因子为例，展示完整的图结构：

```
# 脚本层
(mom_script:`脚本` {
    Name: "momentum.py",
    Content: "from QSExt.FactorDef...\ndefFactor(fdi): ...",
    EntryFunction: "defFactor",
    ModuleType: "FactorDef"
})

(dep_script:`脚本` {
    Name: "return.py",
    Content: "from QSExt.FactorDef...\ndefFactor(fdi): ...",
    EntryFunction: "defFactor",
    ModuleType: "FactorDef"
})

(mom_script)-[:`依赖脚本` {FactorNames: ["Return_1D"]}]->(dep_script)

# 因子层
(momentum:`因子` {FactorClass: "DerivativeFactor", Name: "Momentum5"})
    -[:`定义于`]->(mom_script)
    -[:`依赖` {order: 0}]->(return_1d:`因子` {FactorClass: "FactorTableFactor", Name: "Return_1D"})
    -[:`使用算子`]->(sub_op:`算子` {Name: "sub"})
(return_1d)-[:`定义于`]->(dep_script)

# 数据层
(return_1d)-[:`属于因子表`]->(ft:`因子表` {Name: "DailyBar"})
(ft)-[:`属于因子库`]->(fdb:`因子库` {Name: "JYDB"})

# 存储层
(storer:`因子存储器` {TargetTable: "AlphaFactors"})
    -[:`依赖`]->(momentum)
    -[:`写入因子表`]->(target_ft:`因子表` {Name: "AlphaFactors"})
(momentum)-[:`存入因子表`]->(target_ft)
```

### 4.2 可查询的问题

上述图结构可以自然回答：

| 问题 | Cypher 路径 |
|------|-------------|
| 因子由哪个脚本定义？ | `(因子)-[:定义于]->(脚本)` |
| 脚本依赖了哪些其他脚本？ | `(脚本)-[:依赖脚本*]->(脚本)` |
| 修改脚本 A 会影响哪些因子？ | `(脚本)<-[:定义于*]-(因子)` |
| 某个因子的完整定义链路？ | `(因子)-[:定义于]->(脚本)-[:依赖脚本*]->(脚本)<-[:定义于]-(因子)` |
| 脚本依赖了哪些因子库？ | `(脚本)-[:使用因子库]->(因子库)` |
| 某因子库被哪些脚本使用？ | `(因子库)<-[:使用因子库]-(脚本)` |

## 5. API 设计

### 5.1 存储 API

#### `storeScript(script_path, content=None, meta=None) -> str`

注册单个脚本节点。

```python
def storeScript(self, script_path: str, content: Optional[str] = None,
                meta: Optional[dict] = None, user_id: Optional[str] = None) -> str:
    """注册脚本节点到图数据库

    Args:
        script_path: 脚本文件路径（用于提取文件名和读取内容）
        content: 脚本内容（为 None 时从 script_path 读取）
        meta: __FACTOR_META__ 或 __STRATEGY_META__ 内容（为 None 时尝试从脚本中提取）
        user_id: 资源归属用户 ID

    Returns:
        脚本节点的 QSID
    """
```

**处理逻辑**：
1. 若 `content` 为 None，从 `script_path` 读取文件内容
2. 计算 `ContentHash = sha256(content)`
3. 检查图中是否已存在相同 `ContentHash` 的脚本节点
4. 若已存在且内容未变，更新 `Path`/`MetaJSON` 等可变属性，返回已有 QSID
5. 若不存在，创建新节点，建立与依赖脚本、因子库的关系

#### `storeFactors` 扩展

在现有 `storeFactors` 流程中增加脚本关联逻辑：

#### `getScriptFactors(script_qsid) -> List[Dict]`

获取脚本定义的所有因子。

```cypher
MATCH (f:`因子`)-[:`定义于`]->(s:`脚本` {QSID: $qsid})
RETURN f
```

#### `getScriptDeps(script_qsid, depth=1) -> Dict`

获取脚本的依赖链（递归）。

```cypher
MATCH path = (s:`脚本` {QSID: $qsid})-[:`依赖脚本*1..{depth}`]->(dep:`脚本`)
RETURN dep, length(path) AS depth
ORDER BY depth
```

获取因子的定义脚本（含内容）。

```cypher
MATCH (f:`因子` {QSID: $qsid})-[:`定义于`]->(s:`脚本`)
RETURN s
```

## 6. 重建机制

### 6.1 两种重建模式

```python
def reconstructFactor(self, qsid: str, mode: str = "auto",
                      descriptor_map: Optional[Dict] = None) -> Factor:
    """从图中的元数据重建可计算的 Factor 对象

    Args:
        qsid: 目标因子的 QSID
        mode: 重建模式
            - "metadata": 纯元数据重建（现有方式）
            - "script": 脚本重建（需要 DefScriptQSID）
            - "auto": 优先脚本，无脚本回退元数据
        descriptor_map: 可选的预构建描述子映射

    Returns:
        可直接在计算引擎中使用的 Factor 实例
    """
```

### 6.2 脚本重建流程

```
1. 从图中读取因子的 DefScriptQSID
2. 获取脚本节点内容（Content 字段）
3. 将内容写入临时文件或直接 exec 加载模块
4. 从图中构建 FactorDefInput：
   a. 恢复 FDB 连接（复用 _autoBuildFactorDB）
   b. 递归重建依赖因子（Factors 字典）
   c. 从 MetaJSON 提取 ModelArgs
5. 调用 defFactor(fdi) 得到 Factor 列表
6. 用 QSID 匹配返回目标因子
```

### 6.3 上下文构建

脚本重建的核心难点是构建 `FactorDefInput`。需要从图中递归恢复：

```python
def _buildFactorDefInput(self, script_qsid: str) -> "FactorDefInput":
    """从图中构建 FactorDefInput 上下文"""
    from QSExt.FactorDef.FactorDefContent import FactorDefInput

    # 1. 获取脚本元信息
    script_data = self.getScriptByQSID(script_qsid)
    meta = json.loads(script_data.get("MetaJSON", "{}"))

    # 2. 恢复依赖的因子库连接
    fdb_map = {}
    fdb_deps = self._getScriptFDBDeps(script_qsid)
    for fdb_name, purpose in fdb_deps.items():
        fdb_map[fdb_name] = self._restoreFDB(fdb_name)

    # 3. 递归恢复依赖因子
    factor_map = {}
    factor_deps = meta.get("FactorDeps", {})
    for dep_script_name, dep_factor_names in factor_deps.items():
        dep_script_qsid = self._findScriptByName(dep_script_name)
        if dep_script_qsid:
            for fname in dep_factor_names:
                factor_map[fname] = self._restoreFactorFromScript(
                    dep_script_qsid, fname
                )

    # 4. 构建 ModelArgs
    model_args = meta.get("ModelArgs", {})

    return FactorDefInput(
        FDB=fdb_map,
        Factors=factor_map,
        ModelArgs=model_args,
    )
```

### 6.4 与元数据重建的对比

| 维度 | 元数据重建 | 脚本重建 |
|------|-----------|---------|
| **速度** | 快（直接反序列化） | 慢（需导入模块、连接数据库、执行计算） |
| **鲁棒性** | 依赖类路径不变 | 依赖脚本可执行 |
| **适用范围** | 所有因子 | 仅 FactorDef/StrategyDef 来源的因子 |
| **环境要求** | 类所在模块可导入 | 需要完整的 FactorDefInput 上下文 |
| **容灾能力** | 源文件丢失则无法重建 | 脚本内容在图中，可独立重建 |
| **幂等性** | 严格幂等 | 取决于 defFactor 实现（应保证幂等） |

**建议**：默认使用 `mode="auto"`，优先脚本重建，失败时回退元数据重建。

## 7. 与现有机制的关系

### 7.1 与 FactorStorer 的关系

脚本节点补全了 FactorStorer 到因子定义的追溯链路：

```
现状：
  (因子表) <-[:写入因子表]- (因子存储器) -[:依赖]-> (因子) -[:使用算子]-> (算子)

补全后：
  (因子表) <-[:写入因子表]- (因子存储器) -[:依赖]-> (因子) -[:定义于]-> (脚本) -[:依赖脚本]-> (脚本)
```

### 7.2 与策略节点的关系

策略节点已有 `DefScriptPath` 属性（字符串路径），脚本节点是其升级版：

- `DefScriptPath` → 仅存路径，文件丢失则不可恢复
- `脚本节点` → 存完整内容 + 结构化依赖关系

建议：策略节点的 `DefScriptPath` 保留为兼容字段，新增 `DefScriptQSID` 指向脚本节点。

### 7.3 与 LLMFactor 的关系

`FactorObject.replay(fdi)` 已经实现了"从脚本目录加载并重跑 defFactor"的模式。脚本节点可以视为 `FactorObject` 的图数据库持久化版本：

| FactorObject（文件系统） | 脚本节点（图数据库） |
|--------------------------|---------------------|
| `factor_def.py` 文件 | `Content` 属性 |
| `metadata.json` 文件 | `MetaJSON` 属性 |
| `dir_path` 目录路径 | `Path` 属性 |
| `replay(fdi)` 方法 | `reconstructFactor(qsid, mode="script")` |

## 8. 版本管理策略

### 8.1 图库 vs Git 的分工

| 职责 | Git | 图库（脚本节点） |
|------|-----|-----------------|
| 历史版本 | ✅ 完整历史 | ❌ 仅存最新版 |
| 分支管理 | ✅ | ❌ |
| 代码审查 | ✅ PR/MR | ❌ |
| 运行时恢复 | ❌ 需要 checkout | ✅ 直接读取 |
| 依赖关系 | ❌ 需要解析代码 | ✅ 结构化存储 |
| 跨仓库关联 | ❌ | ✅ 因子-脚本-因子库 |

**原则**：Git 管版本历史，图库管运行时恢复和依赖分析。两者互补，不替代。

### 8.2 内容变更检测

```python
def _shouldUpdateScript(self, existing_hash: str, new_content: str) -> bool:
    """判断脚本是否需要更新"""
    new_hash = hashlib.sha256(new_content.encode("utf-8")).hexdigest()
    return existing_hash != new_hash
```

当脚本内容变更时：
1. 更新 `Content` 和 `ContentHash`
2. 重新解析 `MetaJSON`（FactorDeps 可能变化）
3. 更新 `依赖脚本` 关系
4. 下游因子的 `DefScriptQSID` 不变（QSID 基于内容，内容变则 QSID 变，需重新 storeFactorDef）

### 8.3 脚本内容大小考虑

- 典型 FactorDef 脚本：50-500 行，< 20KB → 无压力
- Neo4j 字符串属性上限：~2GB → 技术上无问题
- 建议：超过 100KB 的脚本给出警告，提示是否确认存储

## 10. 待讨论问题

1. **脚本节点是否需要 `Version` 属性？** — 当前设计基于内容哈希，同一内容只有一个节点。如果需要保留历史版本，可以加 `Version` + `PreviousQSID` 链表结构，但这会增加复杂度，建议先不做。

2. **脚本间的隐式 import 依赖是否建模？** — 当前只建模 `FactorDeps` 显式声明的依赖。`from QSExt.Tools.xxx import yyy` 这类框架依赖不建模，因为它们是框架代码而非业务脚本。

3. **脚本重建失败时的错误处理？** — 建议在 `mode="auto"` 下，脚本重建失败记录日志后静默回退到元数据重建，不阻断流程。

4. **策略脚本的处理？** — 策略定义脚本（`defStrategy`）与因子定义脚本使用同一个 `脚本` 节点类型，通过 `ModuleType` 字段区分。
