## 一、概述

### 1.1 设计目标

假设生成阶段（假设生成）是因子挖掘系统三阶段闭环的第一环，负责基于知识库（QSWiki）、已有因子库（FactorRegistry）、数据字典（JYDB）和历史挖掘记录（Mining Log），自动生成结构化的因子研究假设文档，作为 因子开发阶段 因子开发的输入。

### 1.2 两阶段实现策略

假设生成阶段 分两个阶段实现，共享数据模型和 prompt 模板：

| 阶段 | 运行模式 | 编排方式 | LLM 能力 | 适用场景 |
|---|---|---|---|---|
| **第一阶段** | Skill + Claude Code | Claude 自主调用 MCP 工具 | 自主决策 + tool use + 多轮反思 | 开发调试、交互式探索、单次高质量假设 |
| **第二阶段** | LangGraph | 图节点 + 条件边 | 可控的自主决策（节点内） | 批量生产、可复现、成本可控 |

**共享层**（两种模式复用）：
- 数据模型（`models.py`）：HypothesisDoc、ResearchContext、DirectionCandidate 等
- Prompt 模板（`prompts/`）：Step 1/3/4 的提示词
- 配置（`config.py`）：ResearchConfig
- 辅助工具（`divmode.py`、`budget.py`）：多样化模式、预算分配

**第一阶段优势**：
- 四个 MCP server（mining-log、weknora、qs-registry、jy_base_doc）已上线，Claude Code 可直接调用
- Claude 天然具备 tool use + 自主决策能力，不需要额外编排代码
- 开发量最小 — 主要是 Skill 定义（提示词 + 工具约束）

**第二阶段优势**：
- 成本可控 — LLM 调用次数和 token 可预测
- 可复现 — 相同输入产出相同流程（不同输出）
- 可批量 — 无人值守运行多轮假设生成

### 1.3 核心设计原则

1. **基础设施复用**：直接使用已有的 MCP 工具（第一阶段）或 Python 底层类（第二阶段）
2. **确定性校验与 LLM 反思分离**：新颖性校验纯确定性，避免 LLM 自我确认偏差
3. **多样化在 prompt 层注入**：频繁结构规避和多样化指令在 prompt 中写入
4. **数据契约对齐**：`HypothesisDoc.to_development_input()` 严格对齐方案 7.1 节

## 四、第一阶段：Skill + Claude Code 模式

### 4.1 设计理念

在 Skill 模式下，**Claude Code 自身就是 Agent**。不需要 Python 编排代码 — Claude 自主决定：
- 需要调用哪些 MCP 工具
- 检索结果是否充分，是否需要再搜一轮
- 假设质量是否达标，是否需要多轮反思
- 新颖性校验不通过时如何调整

Skill 文件定义的是**任务指令 + 工具约束 + 输出格式**，而非执行流程。

### 4.2 Skill 层次

```
/hypothesis                        ← 主 Skill（完整流水线 + --step 单步调用）
├── --step explore                 ← Step 1 方向探索
├── --step research                ← Step 2 深度调研
├── --step generate                ← Step 3 假设生成
└── --step check                   ← Step 4 新颖性校验
```

主 Skill 串联全部子步骤；通过 `--step` 参数可独立调用某个步骤，用于调试和迭代。

**Skill 目录结构**（符合 Claude Code Skill 标准格式）：

```
skill/
└── hypothesis/                      # 主 Skill
    ├── SKILL.md                     # Skill 定义（含 YAML frontmatter + --step 模式）
    └── references/                  # 各步骤详细参考文档
        ├── explore_direction.md
        ├── deep_research.md
        ├── generate_hypothesis.md
        └── check_novelty.md
```
    └── SKILL.md
```

每个 SKILL.md 文件包含：
- **YAML frontmatter**：`name`（Skill 名称）和 `description`（触发条件描述）
- **Markdown 指令**：详细的执行流程和输出格式定义

### 4.3 主 Skill：`/hypothesis`

**文件**：`skill/hypothesis/SKILL.md`

**触发词**：`/hypothesis`、`因子假设生成`、`生成因子假设`、`假设生成阶段`

**YAML frontmatter**：

```yaml
---
name: hypothesis
description: |
  假设生成阶段 因子假设生成。基于知识库（QSWiki）、已有因子库（FactorRegistry）、数据字典（JYDB）和历史挖掘记录（Mining Log），自动生成结构化的因子研究假设文档。
  当用户提到以下场景时使用此 skill：因子假设生成、因子研究方向探索、生成因子假设、假设生成阶段、因子挖掘假设、研究假设文档生成、因子 idea 生成、因子 brainstorm。
---
```

**指令概述**：

```
你是因子挖掘系统 假设生成阶段 的假设生成 Agent。你的任务是生成一个或多个
结构化的因子研究假设文档。

## 可用工具
你有以下 MCP 工具可用：
- mining-log: search_history, get_accepted_factors, get_successful_components,
  get_failure_lessons, get_direction_coverage, get_evolution_trail
- weknora: hybrid_search, wiki_search, wiki_read_page, list_knowledge_bases
- qs-registry: search_factors, get_factor_info, get_factor_code
- jy_base_doc: search_table_list, query_table, query_qs_read_data_help,
  query_qs_get_factor_help

## 流程
按以下步骤执行，每步你可以自主决定调用哪些工具、调用几次：

### Step 1: 方向探索
1. 用 weknora/hybrid_search 或 weknora/wiki_search 搜索与研究目标相关的方法论
2. 用 qs-registry 搜索已有的同类因子
3. 用 mining-log 检索历史挖掘记录（方向覆盖率、失败教训）
4. 综合以上信息，提出 3~5 个候选方向

### Step 2: 深度调研（对每个候选方向）
1. 用 weknora/wiki_read_page 深入阅读关联的知识库页面
2. 用 qs-registry/get_factor_code 获取相近因子的源代码
3. 用 jy_base_doc 确认所需数据字段在聚源数据库中可用
4. 用 mining-log 检索该方向的历史成功/失败记录

### Step 3: 假设生成
基于调研结果，生成一个因子研究假设。假设必须包含：
- 经济逻辑（为什么有效）
- 计算伪代码（算子级别）
- 数据需求（字段/频率/股票池）
- 预期特征（IC 方向/量级/换手率）
[详细 YAML schema 见 step3_hypothesis.py 模板]

### Step 4: 反思与校验
1. 自我批判：审查假设的金融逻辑、数据可行性、前瞻偏差风险
2. 修正假设（如有问题）
3. 用 mining-log/search_history 检查与已有因子的相似度（预警）
4. 用 mining-log/get_failure_lessons 检查与失败方向的重叠（可阻断）

### 最终输出
将假设写入本地 YAML 文件，并通过 mining-log 的 MCP 工具记录到挖掘日志库。
输出路径由用户指定，文件名格式：hypothesis_{YYYYMMDD}_{HHMMSS}.yaml
```

### 4.4 步骤设计

各步骤的详细执行规范见 `skill/hypothesis/references/` 目录下的参考文档。通过 `--step` 参数可独立调用某个步骤。

#### Step 1: 方向探索（`--step explore`）

**参考文档**：`references/explore_direction.md`

输入：研究配置（目标类别、市场、频率、数据域）
输出：3~5 个候选方向的 JSON 列表
工具：weknora, qs-registry, mining-log

#### Step 2: 深度调研（`--step research`）

**参考文档**：`references/deep_research.md`

输入：方向描述 + 方向标签
输出：调研报告（wiki 结果、因子代码、数据字段、历史记录）
工具：weknora, qs-registry, jy_base_doc, mining-log

#### Step 3: 假设生成（`--step generate`）

**参考文档**：`references/generate_hypothesis.md`

输入：调研报告
输出：YAML 格式的假设文档
关键约束：需规避频繁结构、多样化模式、经济逻辑引用知识库

#### Step 4: 新颖性校验（`--step check`）

**参考文档**：`references/check_novelty.md`

输入：假设文档 YAML
输出：校验结果（通过/预警/阻断）
检查项：语义相似度、失败方向重叠、数据可行性

### 4.5 Skill 与共享层的关系

Skill 文件（`SKILL.md`）引用共享层的 prompt 模板和数据格式定义：

```
skill/hypothesis/SKILL.md
    │ 引用
    ├── prompts/step1_direction.py   ← Step 1 输出格式
    ├── prompts/step3_hypothesis.py  ← Step 3 YAML schema
    ├── prompts/step4_reflection.py  ← Step 4 审查维度
    └── models.py                    ← HypothesisDoc 字段定义
```

Skill 中嵌入关键格式约束，避免 Claude 需要读取额外文件。完整的 prompt 模板在 `prompts/` 下，供 Skill 文件引用和第二阶段复用。

### 4.6 SKILL.md 文件格式规范

每个 SKILL.md 文件遵循 Claude Code Skill 标准格式：

```markdown
---
name: skill-name
description: |
  Skill 的功能描述。当用户提到以下场景时使用此 skill：触发场景1、触发场景2...
---

# Skill 标题

Skill 的详细指令...

## 输入格式
...

## 可用工具
...

## 执行流程
...

## 输出格式
...
```

**格式要点**：
- `name`：Skill 标识符，使用小写字母和连字符
- `description`：触发条件描述，需要"pushy"一些，列出多种触发场景
- 指令部分使用 Markdown 格式，清晰分节
- 工具说明使用表格形式展示
- 输出格式使用代码块示例

### 5.2 图状态定义（接口）

```python
# graph/state.py

from typing import TypedDict, Annotated
from langgraph.graph import add_messages

class HypothesisState(TypedDict):
    """LangGraph 图状态。"""
    # 输入
    config: dict                           # ResearchConfig 序列化
    target_direction: str                  # 可选：指定方向（跳过 Step 1）

    # Step 1 产出
    candidates: list[dict]                 # DirectionCandidate 序列化列表
    current_candidate_idx: int             # 当前处理的方向索引

    # Step 2 产出
    research_context: dict                 # ResearchContext 序列化

    # Step 3 产出
    draft_hypothesis: dict                 # 假设草稿 YAML → dict

    # Step 4 产出
    critique: dict                         # 批判结果
    refined_hypothesis: dict               # 精炼后的假设
    novelty_result: dict                   # NoveltyCheckResult 序列化

    # 最终产出
    completed_hypotheses: list[dict]       # 所有完成的假设
    skipped_directions: list[dict]         # 被跳过的方向及原因

    # 消息（LangGraph 内部用）
    messages: Annotated[list, add_messages]
```

### 10.8 常见问题

#### Q: Skill 没有触发？

检查：
1. SKILL.md 的 `description` 字段是否包含足够的触发场景
2. MCP 工具是否正确配置并可用
3. 输入格式是否正确（`/hypothesis <类别>, <市场>, <频率>`）

#### Q: 假设质量不佳？

尝试：
1. 增加 Step 2 的调研深度（更多 wiki 页面、更多因子代码）
2. 使用不同的多样化模式（`creative` 或 `divergent` 模式通常产生更创新的假设）
3. 检查知识库是否有足够的相关页面

#### Q: LangGraph 模式报错 "MCP 工具未找到"？

原因：对应的 MCP server 未在 `.mcp.json` 中配置或连接失败。

检查：
1. 确认 `.mcp.json` 中配置了所需的 MCP server
2. 检查 MCP server 进程是否可正常启动
3. 查看日志中的 "连接失败，跳过" 信息

#### Q: LangGraph 模式报错 "StructuredTool does not support sync invocation"？

原因：MCP 工具只支持异步调用，节点函数必须是 `async def`。

检查：确保 `graph/nodes.py` 中所有节点函数都使用 `async def` 定义。

#### Q: 新颖性校验总是阻断？

可能原因：
1. 知识库中已有高度相似的因子 → 尝试更细分的方向
2. 失败教训匹配过于严格 → 可手动调整阈值

## 十二、关键设计决策

| 决策 | 选择 | 依据 |
|---|---|---|
| 第一阶段实现方式 | Claude Code Skill | 四个 MCP server 已上线，Claude 天然具备 tool use 能力，开发量最小 |
| Skill 粒度 | 主 Skill + 子 Skill | 兼顾完整流程和单步调试 |
| 脚本调用方式 | Claude Agent SDK | 直接加载 skill，异步流式输出，支持预算控制 |
| 第二阶段实现方式 | LangGraph | 图结构天然适合条件分支和循环，生态成熟 |
| 共享层范围 | 数据模型 + prompt + 配置 + 辅助工具 | 两种模式的核心逻辑一致，只是编排方式不同 |
| 新颖性校验 | 确定性检查，两种模式一致 | 避免 LLM 自我确认偏差 |
| MCP 调用方式 | 两种模式均通过 MCP 协议调用 | Skill 模式通过 Claude Code 原生调用；LangGraph 模式通过 langchain-mcp-adapters 调用 |
| 知识库 MCP | weknora（替代 qswiki） | weknora 提供更丰富的检索能力（hybrid_search、wiki_read_page） |
