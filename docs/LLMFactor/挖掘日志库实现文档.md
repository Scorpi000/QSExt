## 二、数据库表设计

### 2.1 概述

两张表均部署在 **KDB PostgreSQL 数据库**（`POSTGRESQL_KDB_DSN_DEV`）的 `public` schema 中，**复用 KDB 文档数据库的统一字段结构**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PRIMARY KEY | 记录唯一 ID |
| `source` | TEXT | 数据来源，固定 `factor_mining_system` |
| `source_path` | TEXT | 来源路径（预留） |
| `doc_type` | VARCHAR(200) | 文档类型：`mining_log` / `mining_experience` |
| `content` | TEXT | 文本内容（供全文检索和 embedding） |
| `tags` | TEXT[] | 标签列表 |
| `tsv_content` | TSVECTOR | 全文检索索引字段（自动维护） |
| `embedding` | VECTOR(1024) | bge-m3 文本向量（语义检索） |
| `metadata` | JSONB | 业务字段（核心数据都在这里） |
| `created_at` | TIMESTAMPTZ | 创建时间 |

**设计原因**：业务字段全部放在 `metadata JSONB` 中而非独立列，是为了与 KDB 文档数据库的现有表（news、clustered_news、research_report 等）保持字段结构一致。JSONB 支持高效索引，查询时可使用 `metadata->>'field'` 路径表达式。

### 2.2 mining_log 表 — 挖掘运行记录

每条记录对应一次完整的 **hypothesis → development → evaluation** 闭环。

`metadata` 中的业务字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `hypothesis_id` | text | 关联假设文档 ID |
| `parent_run_id` | text | 父运行 ID — 本次挖掘基于哪次运行改进/精炼。null 表示全新方向探索 |
| `status` | text | 运行状态：pending/in_development/evaluating/completed/failed |
| `decision` | text | 入库决策：accepted/refining/rejected |
| `decision_reason` | text | 决策原因 |
| `factor_name` | text | 因子名称 |
| `category` | text | 因子类别（动量、估值、质量...） |
| `direction_tag` | text | 方向标签（如 "动量/日内方向预测"） |
| `factor_type` | text | standard / synergistic（协同型） |
| `rankic_mean` | float | 样本内 RankIC 均值 |
| `rankicir` | float | ICIR |
| `oos_rankic` | float | 样本外 RankIC |
| `incremental_ic` | float | 组合增量 IC（多样性主判据） |
| `incremental_ic_t` | float | 增量 IC 的 t 统计量 |
| `max_correlation` | float | 与已有因子最大相关性（仅参考） |
| `composite_score` | float | 五维综合评分 0~1 |
| `hypothesis` | jsonb | 完整假设文档 |
| `development` | jsonb | 开发阶段产物（代码路径、参数搜索等） |
| `evaluation` | jsonb | 评测阶段完整数据 |
| `exploration_trail` | jsonb | 检索溯源记录 |
| `code_versions` | jsonb | 代码版本链 |
| `timing` | jsonb | 各阶段耗时 |
| `llm_usage` | jsonb | LLM 使用统计 |

**状态流转**：

```
pending → in_development → evaluating → completed
                                        → failed (syntax/leak/execution error)
```

入库决策字段 `decision` 在评测完成后设置为 `accepted` / `refining` / `rejected`。

**`parent_run_id` 演化链**：串联因子的完整演化历史。一次挖掘可能是在之前某次挖掘基础上的改进或继续尝试：

```
初始假设 (parent_run_id = null)
    │
    ├─ 精炼1 (parent_run_id = 初始假设)
    │     │
    │     └─ 精炼2 (parent_run_id = 精炼1) → 入库
    │
    └─ 另一种尝试 (parent_run_id = 初始假设) → 放弃
```

`get_evolution_tree(run_id)` 方法从任意节点向上追溯到根，再向下递归构建完整的演化树。

### 2.3 mining_experience 表 — 经验库

通过 `metadata->>'track'` 区分成功/失败两条轨道。

`metadata` 中的公共字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `track` | text | success / failure |
| `type` | text | 经验类型（见下方） |
| `name` | text | 经验名称 |
| `description` | text | 经验描述 |
| `direction_tag` | text | 关联方向标签 |
| `quality_score` | float | 质量评分 0~1 |
| `usage_count` | int | 被引用次数 |
| `last_used_at` | text | 最近使用时间 |
| `verification_status` | text | pending / verified / deprecated |
| `source_mining_ids` | text[] | 来源运行 ID 列表 |
| `deprecated_by` | text | 被哪条记录替代 |

**成功经验**（track=success）类型：

| type | 说明 |
|------|------|
| `logic_component` | 可复用逻辑组件（如隔夜日内分解） |
| `tool_function` | 工具函数（如单位换算） |
| `formula_pattern` | 已验证的公式结构 |

额外字段：`code_snippet`（代码片段）、`financial_rationale`（金融逻辑）

**失败经验**（track=failure）类型：

| type | 说明 |
|------|------|
| `dead_end` | 已证明无效的探索方向 |
| `similar_candidate` | 与历史失败因子的相似度 |
| `recovery_pattern` | 从失败中恢复的策略 |

额外字段：`failure_type`（low_ic/no_incremental_ic/overfitting/data_leakage/logic_flaw）、`lesson_learned`（教训）、`recovery_strategy`（恢复策略）

## 三、模块设计

### 3.1 层次关系

```
┌─────────────────────────┐
│     MiningLogRetriever  │  ← 假设生成阶段 使用（检索接口）
│   (RunSummary 等)       │     + 语义检索 (search_by_embedding 等)
├─────────────────────────┤
│    ExperienceRefiner    │  ← 因子评测阶段 完成后经验提炼
│    + LLMReviewer ✅     │     + LLM 审查 (LangChain 统一接口)
├─────────────────────────┤
│  MiningLogRepository    │  ← CRUD 操作 + 向量检索 + backfill
├─────────────────────────┤
│     MiningLogDB         │  ← 连接管理 + DDL
│   EmbeddingService      │     + 向量嵌入 (bge-m3)
│     create_llm() ✅     │     + LLM 工厂 (Ollama / OpenAI 兼容)
├─────────────────────────┤
│  models (MiningRun,     │  ← 数据模型 + 序列化
│   Experience, enums)    │
└─────────────────────────┘
        │
        ▼
  PostgreSQL (KDB)
  ├── mining_log       (+ VECTOR(1024) embedding)
  └── mining_experience(+ VECTOR(1024) embedding)
```

### 3.2 models.py — 数据模型

核心类：

- **`MiningRun`** (Pydantic BaseModel)：一次挖掘运行记录。表级字段（id/source/doc_type/content/tags/metadata）直接映射数据库行，业务字段全部通过 `metadata` dict 直接访问。`parent_run_id` 追溯演化关系，null 表示全新方向。提供 `to_db_row()` 和 `from_db_row()` 方法处理 JSONB 序列化。`meta` 属性为 `metadata` 的简短别名。`embedding_str` 字段存储 pgvector 格式的向量字符串，`to_db_row()` 在有值时自动包含 `embedding` 字段。
- **`Experience`** (Pydantic BaseModel)：经验库记录，同模式。同样支持 `embedding_str` 字段。
- **枚举类**：`RunStatus`、`Decision`、`FactorType`、`ExperienceTrack`、`ExperienceType`、`FailureType`、`VerificationStatus`

使用示例：

```python
run = MiningRun(id='FM_20260704_001')
run.metadata['factor_name'] = 'pe_ttm'
run.metadata['rankic_mean'] = 0.045
print(run.metadata['rankic_mean'])       # 0.045
print(run.metadata.get('status', 'pending'))

# 序列化到数据库行
row = run.to_db_row()
# row['metadata'] == '{"factor_name": "pe_ttm", "rankic_mean": 0.045, ...}'

# 从数据库行还原
run2 = MiningRun.from_db_row(row)
```

### 3.3 db.py — 数据库连接

- **`MiningLogDB`**：连接管理器，惰性创建 `psycopg2` 连接。
  - `__init__(dsn=None)`：默认从 `config/.env` 的 `POSTGRESQL_KDB_DSN_DEV` 读取连接串
  - `connect()`：获取连接（惰性创建）
  - `init_tables()`：建表 + 索引 + 全文检索触发器（幂等，全部 `IF NOT EXISTS`）
  - 支持 `with` 上下文管理器
- **`DDL_CREATE_TABLES`**：完整的建表 SQL 字符串，包含两张表、所有索引、全文检索触发器、向量检索索引（HNSW）

### 3.4 embedding.py — 向量嵌入服务

`EmbeddingService` 基于 Ollama 的 bge-m3 模型将文本内容编码为 1024 维向量，存入 `VECTOR(1024)` 字段，配合 pgvector HNSW 索引实现余弦相似度语义检索。

配置来源（`config/.env`）：
- `OLLAMA_BASE_URL`：默认 `http://127.0.0.1:11434`
- 模型：`bge-m3`（固定）

| 方法 | 说明 |
|------|------|
| `encode(text)` | 单段文本 → numpy 向量 (1024,) |
| `encode_batch(texts)` | 批量编码 → (n, 1024) |
| `to_db_format(vec)` | numpy 向量 → pgvector 兼容字符串 |

**与 Repository 集成**：`MiningLogRepository` 构造函数接受可选 `EmbeddingService`，`insert_run()` / `insert_experience()` 在有 content 且无 embedding 时自动生成向量。`backfill_embeddings()` 方法可为历史记录补写。

### 3.6 retriever.py — 检索接口

`MiningLogRetriever` 是 假设生成阶段 假设生成的核心依赖，封装了对 `MiningLogRepository` 的组合查询（构造函数接受可选 `EmbeddingService`）。

#### 检索结果类型（dataclass，轻量，不包含完整 metadata）

- **`RunSummary`**：运行记录摘要（run_id, factor_name, category, rankic_mean, decision 等）
- **`DirectionStats`**：方向统计（attempts, successes, success_rate）
- **`FailureTrajectory`**：失败轨迹摘要（failure_type, lesson_learned, recovery_strategy）
- **`ExperienceComponent`**：成功经验组件（name, code_snippet, quality_score 等）

#### 核心检索方法

| 方法 | 说明 | 检索策略 |
|------|------|----------|
| `search_by_direction(query, top_k)` | 按研究方向搜索历史记录 | 全文检索 + 标签匹配，去重合并 |
| `search_accepted_in_direction(tag)` | 特定方向的成功入库记录 | 方向过滤 + decision=accepted（供 few-shot） |
| `get_successful_patterns(domain, direction, min_quality)` | 成功经验组件 | 类型过滤 + 质量阈值 |
| `get_failed_directions(query)` | 相似方向的失败记录 | 方向标签 + 全文检索兜底 |
| `get_direction_coverage()` | 各方向探索统计 | 全表 GROUP BY + 成功率计算 |
| `get_frequent_patterns(top_k)` | 频繁代码结构 | 方向计数近似（后续接入 AST 分析） |
| `get_top_factors(metric)` | 排行前列的入库因子 | rankic_mean / composite_score / incremental_ic_t |
| `get_factor_evolution_trail(name)` | 因子的完整演化历史 | 按 factor_name 追溯所有运行版本 |
| `get_evolution_tree(run_id)` | 递归构建完整演化树 | 向上追溯根节点 → 向下递归所有子节点 |

#### 语义检索方法 ✅

| 方法 | 说明 | 检索策略 |
|------|------|----------|
| `search_by_embedding(query, table, top_k, score_threshold, track)` | 通用语义搜索 | EmbeddingService 编码 → pgvector 余弦相似度 |
| `search_similar_accepted(query, top_k, score_threshold)` | 语义搜索 accepted 记录（供 few-shot） | 向量检索 + decision=accepted 过滤 |
| `get_similar_failures(query, top_k, score_threshold)` | 语义搜索失败经验（供规避） | 向量检索 + track=failure 过滤 |

### 3.7 experience_refiner.py — 经验提炼

`ExperienceRefiner` 实现设计文档 6.5 节的三层过滤流程：

```
评测完成
    │
    ├─ accepted → _refine_success()
    │     Step 1: 解析 — extract_code_components() 按注释边界拆分逻辑组件
    │     Step 2: 审查 — ComponentReviewer.review_component() LLM 审查
    │     Step 3: 复评 — quality_score >= 0.3 入库，>= 0.7 标记 verified
    │
    ├─ rejected → _refine_failure()
    │     ComponentReviewer.classify_failure() LLM 分析失败原因
    │     写入 dead_end + lesson_learned + recovery_strategy
    │
    └─ refining → _refine_recovery()
          写入 recovery_pattern
```

#### 关键设计

- **LLM 审查通过回调注入**：`ComponentReviewer` 是一个 `Protocol`，定义 `review_component()` 和 `classify_failure()` 两个方法。
- **`LLMReviewer`** ✅：基于 LangChain `BaseChatModel` 的审查器实现，通过 `create_llm()` 工厂支持 Ollama / OpenAI 兼容等多后端。错误时自动降级到规则判断。
- **`NoOpReviewer`**：空操作审查器，在未接入 LLM 时使用。基于确定性规则做基础判断（RankIC < 0.01 → low_ic 等）。
- **`extract_code_components()`**：启发式代码拆分，以 `# ---- ... ----` 分隔注释为边界识别逻辑组件块，通过中英文映射表推导组件名。

### 3.8 llm_client.py — LLM 工厂 ✅

`create_llm()` 工厂函数，根据 `provider` 参数创建对应的 LangChain `BaseChatModel` 实例。

| provider | 返回类型 | 依赖 | 说明 |
|----------|----------|------|------|
| `"ollama"` | `ChatOllama` | langchain-ollama | 本地 Ollama 模型 |
| `"openai"` | `ChatOpenAI` | langchain-openai | OpenAI 兼容接口（DeepSeek/千问/智谱/MIMO 等） |

配置优先级：参数 > 环境变量（`LLM_PROVIDER` / `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`）。

```python
from QSExt.LLMFactor.mining_log.llm_client import create_llm

# 指定 provider
llm = create_llm("ollama", model="qwen3")
llm = create_llm("openai", model="mimo-v2.5-pro",
    base_url="https://token-plan-cn.xiaomimimo.com/v1", api_key="tp-xxx")

# 从 .env 自动读取
llm = create_llm()
```

### 3.9 llm_reviewer.py — LLM 审查器 ✅

`LLMReviewer` 实现 `ComponentReviewer` 协议，通过 LangChain 统一接口调用 LLM。

**核心方法**：

| 方法 | 输入 | 输出 | 说明 |
|------|------|------|------|
| `review_component()` | code_snippet, name, description | `{approved, financial_rationale, issues, suggestions, quality_score}` | 审查组件金融逻辑和代码质量 |
| `classify_failure()` | MiningRun | `{failure_type, lesson_learned, recovery_strategy}` | 分析失败原因并给出恢复策略 |

**辅助函数**：`_extract_json(text)` — 从 LLM 输出中健壮提取 JSON（支持纯 JSON / markdown 代码块 / 周围有文字 / `<think>` 标签）。

**错误处理**：LLM 调用失败时自动降级到与 `NoOpReviewer` 相同的规则判断，不阻断流程。

### 4.7 使用 MiningLogWriter（阶段化写入）

```python
from QSExt.LLMFactor.mining_log import MiningLogWriter, MiningLogDB, MiningLogRepository

db = MiningLogDB()
db.init_tables()
repo = MiningLogRepository(db)
writer = MiningLogWriter(repo)

# 假设生成阶段: 假设生成完成
writer.start_run(
    run_id="FM_20260701_143052",
    factor_name="enhanced_intraday_momentum_v2",
    category="动量",
    direction_tag="动量/日内方向预测",
    hypothesis={"economic_rationale": "...", "calculation_pseudo": "..."},
    tags=["动量", "日内"],
    inspired_by={"wiki_pages": ["momentum-crash"]},
    reflection={"critique_notes": "..."},
)

# 因子开发阶段: 因子开发完成
writer.record_development(
    run_id="FM_20260701_143052",
    code_path="workspace/FM_20260701_143052/stock_cn_factor.py",
    best_params={"LookBack": 120, "decay": 0.94},
    param_search={"method": "TPE", "n_trials": 200, "best_is_rankic": 0.058},
    auto_fix_count=1,
)

# 因子评测阶段: 评测完成
writer.record_evaluation(
    run_id="FM_20260701_143052",
    rankic_mean=0.045,
    rankicir=0.72,
    oos_rankic=0.041,
    incremental_ic_t=2.8,
    composite_score=0.67,
)

# 决策
writer.set_decision(
    run_id="FM_20260701_143052",
    decision="accepted",
    reason="增量 IC 显著 (t=2.8)，综合评分 0.67",
)
```

**阶段化写入方法**：

| 方法 | 阶段 | 必填字段 | 自动操作 |
|------|------|----------|----------|
| `start_run()` | 假设生成阶段 假设生成 | factor_name, category, direction_tag, hypothesis | 设置 status=in_development, 记录 timing |
| `record_development()` | 因子开发阶段 因子开发 | code_path | 设置 status=evaluating, 记录 timing |
| `record_evaluation()` | 因子评测阶段 因子评测 | rankic_mean | 更新评测字段, 记录 timing |
| `set_decision()` | 决策 | decision, decision_reason | 设置 status=completed, 记录 timing |
| `mark_failed()` | 失败 | reason | 设置 status=failed |
| `update_field()` | 任意 | key, value | 更新单个字段 |
| `update_tags()` | 任意 | tags | 更新标签列表 |
