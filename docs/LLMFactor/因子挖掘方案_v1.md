# 因子挖掘方案 v1

> 基于 RD-Agent 模式的 LLM 驱动因子挖掘系统设计方案
>
> 本方案整合 QSWiki 知识库中的核心方法论，以六条核心设计原则为骨架，
> 构建从假设生成到因子入库的完整闭环系统。
>
> **v1 相较 v0 的主要修订**（均以知识库证据为依据）：
> 1. **多样性判定纠偏**：将 `MaxCorr < 0.7` 从入库硬门槛降级为软预警信号，改以「组合增量 IC」作为多样性主关卡（依据 [[mutual-ic-vs-synergy-gap]]）；相关性惩罚可选连续折价 `(1-MaxCorr)*IC`（[[alpha-diversity-correlation-penalty]]）。
> 2. **精炼循环具体化**：精炼态接入维度定向精炼机制（[[dimension-targeted-refinement]]），用 Softmax 概率式选择薄弱维度。
> 3. **生成阶段主动去同质化**：引入频繁结构规避（[[frequent-subtree-avoidance]] 的代码空间改编）与多样化提示词（[[diverse-generation-prompts]]），并诚实标注「因子趋同无法完全消除」这一已知局限。
> 4. **过拟合维度落地**：五维评分的过拟合风险维度接入 [[llm-overfitting-risk-assessment]] 的具体评估方法。
> 5. **假设规划强化**：假设生成阶段 引入 [[reflection-based-planning]] 三阶段自我批判（起草→批判→精炼）。
> 6. **引用与归因修正**：修正「五 Agent」归因、标注搜索预算是脱离 MCTS 的简化版、程序级决策改用更贴切的 [[expression-space-vs-code-space]] 引用。

## 一、概述

### 1.1 设计目标

构建一套基于大语言模型（LLM）的自动化因子挖掘系统，在 QuantStudio 量化研究框架之上，实现从假设生成、因子开发到因子评测的完整闭环。系统的核心目标不是替代人类研究员，而是将因子研究的完整流程标准化、可复盘、可积累，使每一次挖掘都为后续研究提供可复用的知识增量。

### 1.2 核心设计原则

本方案遵循六条核心设计原则，每条均来源于知识库中经过验证的方法论：

| 原则 | 来源 | 核心主张 |
|------|------|----------|
| **基础设施前置** | [[callable-research-stack]] + [[factor-platform-infrastructure]] | Agent 调度上线前，先将数据、算子、评测固化为可独立运行的确定性组件 |
| **宏微观分离** | [[macro-micro-co-evolution]] | LLM 负责逻辑创新（宏观），本地计算负责参数优化（微观），解决速度不匹配 |
| **数据中心化** | [[rd-agent-quant]] | LLM 仅接触 Schema 级信息（字段名、类型、输出格式），不接触原始行情数据 |
| **Agent-Script 分工** | [[factor-iteration-skill]] | Agent 负责因子思路设计、代码生成、结果解读；脚本负责确定性执行和评测 |
| **双轨知识积累** | [[experience-library]] + [[chain-of-experience]] | 成功经验沉淀为可复用组件（"什么有效"），失败轨迹保存为方向约束（"什么无效、为什么"） |
| **审计导向** | [[research-computation-graph]] + [[standardized-research-reporting]] | 每个因子从假设到评测的完整路径可追溯、可复现、可审计 |

### 1.3 范式融合

以上原则落地时，融合了以下具体范式的方法论：

| 范式来源 | 核心贡献 | 本方案采纳要点 |
|----------|----------|----------------|
| **RD-Agent(Q)** | 五单元闭环 + 多臂老虎机调度 | 假设→开发→评测三阶段流水线 + 数据中心化设计 |
| **FactorEngine** | 程序级演化 + 经验链 (CoE) + 宏微观分离 | 代码空间搜索、失败轨迹记录、逻辑-参数解耦 |
| **东吴金工 Factor Iteration Skill** | 标准化工作流 + 工具函数沉淀 + 历史反馈 | Agent-Script 分工、工具库自生长 |
| **CogAlpha** | 七级智能体 + 思维进化 + 质量检查 | 多智能体质量检查器、未来信息泄漏检测、多样化提示词 |
| **LLM-MCTS**（Shi, Duan, Li 2025） | 多维 Alpha 评估 + 经验库三层过滤 + 维度定向精炼 + 频繁结构规避 | 五维评测体系、经验组件提炼、精炼定向、生成去同质化 |
| **AlphaGen(Q)**（Yu et al. KDD 2023） | 集合级协同优化优于单因子过滤 | 以组合增量 IC 取代互 IC 阈值作为多样性判据 |
| **案例驱动生成** | 成功案例 → 少样本学习 → ICIR 跃升 | 假设生成阶段注入已验证案例作为 few-shot 范例 |
| **QRAFTI** | 全管线可复现 + 标准化诊断报告 + 反思式规划 | 评测报告四部分诊断框架、计算图追溯、三阶段自我批判 |

## 二、基础设施层（系统上线前必须建立）

借鉴 [[callable-research-stack]] 的四层架构和 [[factor-platform-infrastructure]] 的三层框架，在 Agent 调度上线前先固化以下底座。四层递进关系：**数据接口 → 因子对象标准 → 搜索轨迹 → 经验知识库**，每一层都是上一层的前提。

### 2.1 L0：数据与面板接口

基于 `jy_base_doc` MCP 工具（`QSAgent/knowledge/jy_base/jy_postgresql_tools.py`），LLM 通过动态探索了解聚源数据库结构，无需预编译静态 Schema 清单。

**MCP 工具集**：

| 工具 | 功能 | LLM 可见信息 |
|------|------|-------------|
| `search_table_list(query, path)` | 语义搜索相关表 | 表名、说明、路径 |
| `query_table(table)` | 查表结构 | 字段名、类型、含义、有值率、唯一性字段 |
| `query_qs_read_data_help(table)` | QS 读取数据说明 | `fdi.FDB["JYDB"].getTable()` 用法 |
| `query_qs_get_factor_help(table)` | QS 获取因子说明 | FactorDef 写法 |
| `execute_sql(sql, top_k)` | 查询数据 | **自动截止**（见下） |

**前视偏差防护**：`execute_sql` 在 MCP 服务启动时读取配置 `AS_OF_DATE`（如 `2024-01-01`），执行 SQL 时自动检测主表中的 `updatetime` 或 `xgrq` 字段，直接在 SQL 的 `WHERE` 子句中注入截止条件。对 LLM 完全透明 — LLM 无感知地只看到截止日期之前的数据。

```
LLM 视角：execute_sql("SELECT tradingday, closeprice FROM qt_dailyquote WHERE innercode = 1 ORDER BY tradingday DESC LIMIT 5")
实际执行：SELECT tradingday, closeprice FROM qt_dailyquote WHERE xgrq <= '2024-01-01' AND innercode = 1 ORDER BY tradingday DESC LIMIT 5

LLM 视角：execute_sql("SELECT * FROM qt_dailyquote LIMIT 10")
实际执行：SELECT * FROM qt_dailyquote WHERE xgrq <= '2024-01-01' LIMIT 10
```

**注入逻辑**：
1. 从 SQL 中提取主表名（`FROM` 后的第一个表，正则匹配）
2. 查该表是否有 `updatetime` 或 `xgrq` 字段 — 优先查 `information_schema.columns`，兜底查 `jy_base_doc` 文档内容（结果缓存）
3. 有 → 在 `WHERE` 子句追加 `AND xgrq <= 'as_of_date'`；无 `WHERE` 则插入 `WHERE` 条件（不加引号，PostgreSQL 自动转小写）
4. 无此字段 → 原样执行（如系统配置表等非时序数据）

**实现位置**：
- `QSAgent/knowledge/jy_base/jy_postgresql_tools.py` — `JYDocToolkit.as_of_date` / `_detect_date_field` / `_inject_date_filter` / `execute_sql`
- `QSAgent/mcp/jy_base_doc_pg.py` — 从 `.env` 读取 `AS_OF_DATE` 传入 toolkit

**配置**（`config/.env`）：

```bash
# 数据截止日期 — LLM 只能看到此日期及之前的数据
AS_OF_DATE=2024-01-01
```

**核心约束**：LLM 能探索数据库结构（表、字段、说明），也能查看数据的样子（量级、分布、格式），但永远看不到截止日期之后的数据。这是从 [[rd-agent-quant]] 借鉴的数据中心化防泄漏设计，通过 MCP 工具层自动执行，不依赖 LLM 自觉。

### 2.2 L1：可执行因子对象标准

基于 因子开发阶段 产出的因子开发目录（参考 `demo_stock_cn_factor_def/`），将目录中的分散产物封装为统一的 `FactorObject` 类。**不新建数据结构，而是标准化已有产物的读取和访问方式。**

**因子开发目录结构**（因子开发阶段 每次运行产出）：

```
local/workspace/FM_{timestamp}/
├── factor_def.py                  # 可执行因子代码
├── README.md                      # 因子说明文档
├── metadata.json                  # 结构化元数据
├── param_search/
│   ├── search_space.json          # 搜索空间定义
│   └── best_params.json           # 最优参数
└── validation/
    ├── syntax_report.json         # 语法检查结果
    ├── leak_test_report.json      # 未来信息泄漏检测报告
    └── semantic_review.md         # 语义审查意见
```

**L1 标准化封装**：

```python
class FactorObject:
    """一个因子的标准表示 — 从开发目录加载。"""

    def __init__(self, dir_path: str):
        """从因子开发目录加载全部产物。"""
        self.metadata = load_json(f"{dir_path}/metadata.json")
        self.code = read_file(f"{dir_path}/factor_def.py")
        self.params = load_json(f"{dir_path}/param_search/best_params.json")
        self.validation = {
            "syntax": load_json(f"{dir_path}/validation/syntax_report.json"),
            "leak_test": load_json(f"{dir_path}/validation/leak_test_report.json"),
            "semantic_review": read_file(f"{dir_path}/validation/semantic_review.md"),
        }

    # ---- 标准属性 ----
    @property
    def name(self) -> str: ...                    # metadata.factor_name
    @property
    def description(self) -> str: ...             # metadata.description
    @property
    def dependencies(self) -> dict: ...           # metadata.data_sources
    @property
    def parameters(self) -> dict: ...             # param_search/search_space.json
    @property
    def hypothesis_id(self) -> Optional[str]: ... # metadata.hypothesis_id

    # ---- 标准方法 ----
    def replay(self, input_data) -> Panel: ...    # 执行 factor_def.py，返回因子值
    def explain(self) -> str: ...                 # 基于 metadata + README 生成标准化说明
    def unit_test(self) -> dict: ...              # 汇总 syntax + leak_test + semantic_review
```

**与 MiningRun 的关系**：`MiningRun.metadata["development"]` 中存储了代码路径和参数搜索结果，`FactorObject` 可以从该路径加载目录，也可以独立于 MiningRun 使用。

**实现位置**：`QSExt/LLMFactor/factor_object/factor_object.py`

**已实现** ✅：

- 属性：`name`、`description`、`formula`、`category`、`market`、`frequency`、`tags`、`hypothesis_id`、`qsid`、`status`、`metadata`、`code`、`readme`、`params`、`search_space`、`validation`（全部懒加载）
- `replay(fdi, dep_fd)` — 动态导入 factor_def.py 并执行 defFactor()，支持 List[Factor] 和 FactorDef 两种返回类型
- `explain()` — 基于 metadata + README 生成标准化说明
- `unit_test()` — 汇总 validation/ 目录下的所有检查结果

- `validate_factor_dir(dir_path)` — 工具函数，校验目录结构完整性

### 2.4 L3：经验知识库

**双轨制设计**，融合两种互补的知识积累范式：

```
经验知识库/
├── success_patterns/          # 成功经验库（借鉴 [[experience-library]]）
│   ├── components/            # 可复用逻辑组件（经三层过滤：解析→审查→复评）
│   ├── formulas/              # 已验证的公式结构
│   └── tool_functions/        # 可复用工具函数（借鉴 [[tool-function-accumulation]] 的自生长机制）
│
├── failure_trajectories/      # 失败轨迹库（借鉴 [[chain-of-experience]]）
│   ├── dead_ends/             # 已证明无效的探索方向
│   ├── similar_candidates/    # 与历史失败因子的相似度阈值
│   └── recovery_patterns/     # 从失败中恢复的成功策略
│
├── frequent_patterns.json     # 频繁代码结构（用于生成去同质化，见 3.6）
└── direction_index.md         # 已探索方向索引（语义可检索）
```

**关键设计**：经验库告诉 LLM "什么有效"（组件级复用），失败轨迹库告诉 LLM "为什么失败、如何避免"（过程级学习）。两者正交互补，不可替代。[[chain-of-experience]] 的消融实验证明，CoE 提示相比仅 top-K 成功案例提示独立提升了 RankIC 和组合表现。

## 三、假设生成阶段 (Hypothesis Generation)

### 3.1 目标

假设生成阶段的目标是：给定当前的研究状态和历史挖掘记录，产出结构化的因子研究方向描述和计算方案，作为下一阶段"因子开发"的输入。

### 3.2 输入源

假设生成阶段整合以下信息源进行推理：

#### 3.2.1 知识检索源

| 信息源 | 内容 | 接入方式 |
|--------|------|----------|
| **QSWiki 知识库** | 因子挖掘方法论、学术论文摘要、框架对比分析、技术实现细节 | `mcp__qswiki__kb_search` / `kb_ask` / `kb_page` |
| **已有因子库** | 已注册因子的元信息、描述、分类、数据源、算子、源代码 | `mcp__factor-registry__search_factors` / `get_factor_info` / `get_factor_code` |
| **JYDB 数据字典** | 聚源数据库的表结构、字段定义、数据频率 | `mcp__jy_base_doc__search_table_list` / `query_table` |

#### 3.2.2 历史挖掘记录（来自双轨日志库）

| 信息源 | 内容 | 用途 |
|--------|------|------|
| **成功经验库** | 已验证有效的因子表达式/代码及评测指标、可复用逻辑组件、工具函数 | 案例驱动生成（Case-Driven Generation），提供 few-shot 学习范例 |
| **失败轨迹库** | dead_ends（已证明无效的方向）、similar_candidates（与历史失败因子的相似度）、recovery_patterns（从失败中恢复的策略） | 避免重复无效探索——不仅知道"什么无效"，还知道"为什么无效"和"如何绕过" |
| **频繁结构库** | 已有因子中出现频率最高的 top-k 代码结构模态 | 生成时主动规避，防止在少数验证有效的模板周围过度聚集（见 3.6） |
| **方向索引** | 各方向的探索次数、成功率、冻结状态 | 方向覆盖率分析，识别高潜力未探索区域 |

#### 3.2.3 研究方向配置

研究员可以通过配置文件指定本轮挖掘的偏好：

```yaml
# 研究方向配置示例
research_direction:
  target: "价值因子"               # 目标因子类别
  market: "A股"                   # 目标市场
  frequency: "日频"               # 数据频率
  data_domains:                   # 允许使用的数据域
    - "价量数据"
    - "财务数据"
  avoid_domains:                  # 排除的数据域
    - "另类数据"
  reference_factors:              # 参考因子（用于增量创新）
    - "pe_ttm"
    - "pb_lf"
  constraints:                    # 约束条件
    # 注意：相关性为软预警，非硬门槛。多样性最终以「组合增量 IC」为准（见 5.5）
    correlation_warning_threshold: 0.7   # 超过此值仅触发预警与增量 IC 复核，不直接拒绝
    min_incremental_ic_t: 2.0            # 组合增量 IC 的显著性要求（多样性主判据）
    min_turnover_days: 5
```

> **v1 修订说明**：v0 使用 `max_correlation_with_existing: 0.7` 作为硬约束。[[mutual-ic-vs-synergy-gap]]（Yu et al. KDD 2023）已系统证明该阈值在数学上不成立——互 IC 高达 0.9746 的两个因子，减法组合后 IC 仍可超越两者之和；且 CSI500 上 0.7 过滤反而降低组合 IC。因此相关性降级为预警信号，真正的多样性关卡是组合增量 IC。

### 3.4 方向搜索预算分配

借鉴 [[dynamic-search-budget-allocation]] 的自适应思想，为每个候选方向分配搜索预算。

> **重要说明（v1 新增）**：[[dynamic-search-budget-allocation]] 原本是 LLM-MCTS 框架内「新 Alpha 得分突破树内历史最高分 → 触发 breakthrough → 增加该子树搜索预算」的机制，与 MCTS 树结构强绑定。本方案当前不实现 MCTS（见附录 A），因此以下是**脱离 MCTS 树的简化改编**：以"方向"替代"子树"，以历史成功率替代"树内节点得分"。待引入 MCTS 后（附录 B），应回归其原始的突破触发机制。

```python
def allocate_search_budget(direction: str, mining_log: MiningLogRetriever) -> float:
    """为每个候选方向分配搜索预算（脱离 MCTS 的简化版）"""
    # 方向潜力 ← QSWiki 中该方法论的置信度、相关论文数量
    wiki_potential = mining_log.get_wiki_coverage(direction)

    # 历史成功率 ← Mining Log 中该方向的 accept/(accept+reject) 比率
    history = mining_log.get_direction_coverage()[direction]
    success_rate = history.successes / max(history.attempts, 1)

    # 未探索程度 ← 1 - (已探索子方向数 / 理论子方向数)
    unexplored_ratio = 1 - (history.attempts / estimate_total_sub_directions(direction))

    # 综合预算（乘法模型，任一维度为 0 则预算接近 0）
    budget = wiki_potential * (0.3 + 0.7 * success_rate) * (0.2 + 0.8 * unexplored_ratio)
    return budget

# 动态调整规则（改编自 LLM-MCTS 的 breakthrough 机制）:
# 1. 新因子得分突破历史最高 → 自动增加该方向预算 (budget *= 1.5)
# 2. 连续 N=3 次失败 → 冻结方向 (status=frozen)，标记"待新知识注入后重开"
# 3. 新论文/新数据源进入知识库 → 重新激活相关冻结方向
```

### 3.6 生成阶段去同质化（v1 新增）

v0 仅依赖"四个创新角度 + 事后新颖性校验"来保证多样性，缺少生成时的主动机制。v1 补入两项，并诚实标注其局限：

**(1) 频繁结构规避** — 改编自 [[frequent-subtree-avoidance]]：
- 从成功经验库/因子库中统计出现频率最高的 top-k 代码结构模态（如"滚动均值比值""截面排序差"），写入 `frequent_patterns.json`。
- 生成时以 prompt 约束方式（而非硬编码过滤）要求 LLM 避免复用这些高频结构。
- **改编与局限说明**：原始 FSA 作用于表达式树的「闭合根基因」，依赖精确的子树结构匹配；本方案是**代码空间（程序级）**，无固定表达式树。因此这里退化为「代码模式/逻辑组件级」的启发式规避。[[frequent-subtree-avoidance]] 自身已指出其盲区——"语义等价但结构不同"的公式能逃过匹配；在代码空间中这一盲区更严重（同一逻辑的写法更自由）。故本机制仅作辅助，不作为多样性保证。

**(2) 多样化提示词** — 引入 [[diverse-generation-prompts]] 的五种改写模式（轻度/中度/创意/发散/具象），每次生成随机选择，配合温度映射。

> **诚实标注的已知局限**：[[diverse-generation-prompts]] 记录了广发证券的实证结论——**即使调整温度与提示词模式，同一模板仍可能导致方向重复，因子趋同问题无法完全解决**。因此本方案不将生成端去同质化视为充分手段，多样性的最终保证仍落在 因子评测阶段 的组合增量 IC 检验（见 5.5）。此局限已纳入第十节风险表。

## 四、因子开发阶段 (Factor Development)

### 4.1 目标

将 假设生成阶段 的结构化假设文档转化为 QuantStudio 框架下可执行、可验证的因子代码，并完成超参数搜索。

### 4.2 核心设计：宏微观分离

借鉴 [[macro-micro-co-evolution]] 的三层分离原则。核心论点：LLM 擅长语义推理和逻辑创新（高层次、小批量），但单个生成-评估周期耗时长；参数优化适合自动化搜索（低层次、大批量），需要大量评估迭代。将两者耦合会导致 LLM 等待回测结果、计算资源闲置。

| 层次 | 负责方 | 任务 | 调用频率 | LLM 参与 |
|------|--------|------|----------|----------|
| **宏观层** | LLM Agent | 因子逻辑设计、算子选择、DAG 结构编排、代码生成 | 每次假设 1-3 次 | ✅ |
| **微观层** | 本地计算 (Optuna/TPE) | 超参数搜索（窗口大小、衰减因子、阈值） | 每次假设数百次 | ❌ |
| **验证层** | 确定性脚本 | 语法检查、执行验证、未来信息泄漏检测 | 每次代码变更 | ❌ |

### 4.3 开发原则

1. **代码空间表达**：LLM 直接生成完整的 Pandas/NumPy 因子函数代码（非固定表达式树），可表达条件逻辑、状态切换、非对称衰减等复杂构造。此决策依据 [[expression-space-vs-code-space]] 对两条路线的对比——代码空间在表达能力上更强，能承载表达式树无法编码的控制流。
2. **框架合规**：严格遵循 QuantStudio FactorDef 规范（`defFactor(fdi, dep_fd) -> FactorDef` 模式）
3. **防泄漏设计**：财务数据使用 `CalcType="最新"`（公告时点）；LLM 不接触原始数据值
4. **双板合并**：A 股因子必须同时覆盖主板和科创板，使用 `fo.Where + fo.NotNull` 合并策略
5. **可执行即正确**：代码必须能通过 Python 导入和执行，无语法错误、无运行时异常

### 4.5 未来信息泄漏检测

这是因子挖掘中最严重的错误，必须作为硬性关卡。参照 [[future-information-leakage-detection]]：

**时序截断单元测试：**

1. 从有效日期中随机抽取 N 个测试日期（如 N=10）
2. 对每个测试日期 T，将全量行情数据截断至 T（移除 T 之后的数据）
3. 使用截断数据重新运行因子代码
4. 比较原始因子值与截断重算后的因子值在日期 T 上的差异
5. **判定标准：** 差异 < 1e-8 且相关系数 > 0.9999 → 无泄漏；否则标记为疑似未来信息泄漏并拒绝

### 5.4 多维评分

借鉴 [[multi-dimensional-alpha-evaluation]] 的五维度评分体系：

```python
@dataclass
class MultiDimEvalScore:
    """五维度综合评分（每个维度 0-1 归一化）"""
    effectiveness: float     # 有效性 — RankIC 均值 + ICIR
    stability: float         # 稳定性 — IC 时序特征
    turnover: float          # 换手率 — 交易成本代理
    diversity: float         # 多样性 — 见下方说明
    overfitting_risk: float  # 过拟合风险 — 见 5.4.1
    composite: float         # 综合得分 — 等权平均
```

**多样性维度（diversity）的口径**（v1 明确）：采用 [[multi-dimensional-alpha-evaluation]] 原始定义 `e_diversity = 1 - R(f, m_diversity, F_zoo)`，即候选因子与因子库最大相关性的**百分位排名归一化**得分（加性维度，权重 1/5），而非二值切断。这与「组合增量 IC 硬关卡」是两个独立机制：前者是评分的一个分量（软），后者是入库的必要条件（硬，见 5.5）。

#### 5.4.1 过拟合风险维度的具体方法（v1 新增）

接入 [[llm-overfitting-risk-assessment]]，这是五维中**唯一不依赖回测数据**的维度：

- **输入**：候选因子完整代码 + 精炼历史 H(s)（从初始假设到当前版本的所有中间版本及评分变化）+ 复杂度指标（DAG 深度、算子数量、参数个数）。
- **LLM 关注的过拟合信号**：代码/结构过度复杂；参数过度调优（存在多个仅参数不同的近似版本）；精炼边际收益递减；结构过度特定（依赖特定参数组合，轻微扰动即恶化）。
- **输出**：`e_overfit = LLM_eval(code, H(s))`，**温度 T=0.1** 确保评分稳定可复现。
- **与量化指标互补**：捕捉 IS/OOS 衰减比等量化指标无法反映的结构性过拟合风险。

> **已知局限**（来自该页 Counterarguments，须在报告中标注）：LLM 判断缺乏形式化泛化理论保证；评分与真实 OOS 衰减的相关性未经验证；存在"同一 LLM 生成又评估"的自我确认偏差。因此本维度**仅作五维之一（权重 1/5）**，不单独作为拒绝依据，须与 IS/OOS 衰减比等量化过拟合信号交叉印证。

#### 5.5.1 精炼的具体机制：维度定向精炼（v1 新增）

v0 的精炼态只写"基于短板生成精炼建议"，未说明**如何选择改哪个维度**。v1 接入 [[dimension-targeted-refinement]]，与已有的五维评分天然契合：

**维度选择（概率式，非确定式）：**

```
P(i* = i | s) = Softmax((e_max · 1_q - E_s) / T)_i
```

- `E_s` = 该因子的五维评分向量；`e_max · 1 - E_s` 为各维度的"缺陷程度"。
- 低分维度获得更高选择概率，但保留探索性（即使最弱维度也非必选）。
- 温度 `T`（默认 1）控制随机性；可考虑随迭代进程动态调整（早期高 T 多探索，后期低 T 聚焦）。

**维度差异化 few-shot 范例策略**（来自该页）：
- 有效性 / 稳定性维度 → 用过滤后的高分范例
- 多样性维度 → 用低相关范例
- 换手率 / 过拟合风险维度 → zero-shot

**上下文**：精炼时向 LLM 提供该因子的精炼历史、父/兄/子版本信息，避免重复建议。精炼后的新假设回流 假设生成阶段，以"改进 hyp_xxx 的 {选中维度}"为定向种子。

> **局限提示**（来自该页 Gaps）：维度间可能存在权衡（如降换手率同时降有效性），而定向精炼假设各维度可独立改进，未显式建模冲突。实践中若一次精炼恶化了其他维度，应回退并换维度。

### 5.6 评测报告模板

参照 QRAFTI 的标准化研究报告框架，每份评测报告包含四个部分：

**一、基本概况** — 因子名称、QSID、类别、频率；评测区间、股票池；覆盖率

**二、预测力评估** — RankIC/ICIR；分年度统计；IC 累计走势图；多空组合收益曲线

**三、稳健性诊断** — 子期覆盖稳健性；市值/行业中性化后 IC；规模分层 Alpha；双重排序检验（[[double-sort]]）；过拟合风险定性评估（5.4.1）

**四、增量信息与综合判定** — 因子库相关性矩阵（参考）；**组合增量 IC 及其 t 统计量（判据核心）**；综合评级；因子优缺点与改进建议

### 6.4 检索接口

```python
class MiningLogRetriever:
    """挖掘日志检索器 —— 假设生成阶段 假设生成的核心依赖"""

    def search_by_direction(self, query: str, top_k: int = 10) -> list[RunSummary]:
        """语义搜索：根据研究方向描述检索相关历史记录"""

    def get_successful_patterns(self, domain: str = None, min_quality: float = 0.7) -> list[ExperienceComponent]:
        """获取成功经验库中的可复用组件"""

    def get_failed_directions(self, query: str) -> list[FailureTrajectory]:
        """检索相似方向上的历史失败记录和失败原因"""

    def get_direction_coverage(self) -> dict[str, DirectionStats]:
        """统计各方向已探索次数和成功率，识别未充分探索的区域"""

    def get_frequent_patterns(self, top_k: int = 3) -> list[CodePattern]:
        """获取因子库中最频繁的代码结构模态（供生成去同质化，见 3.6）"""

    def get_incremental_ic_history(self, factor_qsids: list[str]) -> pd.DataFrame:
        """查询多个因子相对基准池的历史增量 IC（多样性判据的历史依据）"""

    def get_factor_evolution_trail(self, factor_qsid: str) -> EvolutionTrail:
        """追踪一个因子的完整演化历史（从初始假设到最终入库的每次迭代）"""
```

## 八、闭环反馈机制

```
┌──────────┐   假设文档   ┌──────────┐   因子代码   ┌──────────┐
│ 假设生成阶段  │ ──────────→ │ 因子开发阶段  │ ──────────→ │ 因子评测阶段  │
│ 假设生成 │             │ 因子开发 │             │ 因子评测 │
└──────────┘             │ (宏+微)  │             │ (诊断+评分)│
      ▲                  └──────────┘             └──────────┘
      │                                                │
      │           经验提炼 + 方向更新                    │
      └────────────────────────────────────────────────┘
                         │
                    ┌────┴────┐
                    │ 挖掘日志 │
                    │   库    │
                    └────┬────┘
                         │
       ┌─────────────┬───┴────────┬──────────────┐
       ▼             ▼            ▼              ▼
  成功经验库    失败轨迹库    频繁结构库      方向索引
 (组件/公式) (死胡同/教训) (去同质化)   (覆盖率/状态)
```

### 三条反馈路径

| 路径 | 触发条件 | 更新内容 | 假设生成阶段 使用方式 |
|------|----------|----------|-----------------|
| **成功路径** | 因子入库 (decision=accepted) | 可复用组件 → 成功经验库；有效公式 → 模式库；频繁结构库重算；方向成功率 +1 | 引用为 few-shot 范例；规避频繁结构；推荐相似方向 |
| **失败路径** | 因子放弃 (decision=rejected) | 死胡同 → 失败轨迹库；教训 → dead_ends；方向成功率更新 | 相似方向自动预警；避开已证明的无效路径 |
| **精炼路径** | 因子需改进 (decision=refining) | 维度定向精炼选中的维度 + 精炼建议 → 新假设的种子；短板标注 → 方向索引 | 作为下一轮假设生成的定向起点和约束 |

## 十、关键风险与缓解措施

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| **未来信息泄漏** | 因子虚高，实盘无效 | 时序截断单元测试作为硬性关卡；财务数据公告时点；LLM 仅接触 Schema |
| **因子同质化** | 因子库膨胀但无增量 | **组合增量 IC（t>2.0）作为硬关卡**（[[mutual-ic-vs-synergy-gap]]：互 IC 不可靠）；生成端频繁结构规避 + 多样化提示词；多样性纳入五维评分 |
| **相关性判据误用** | 误杀高协同价值因子 / 放行冗余因子 | 相关性仅作预警；以组合增量 IC 为准；协同型因子（单独弱但增量强）允许入库并标记 |
| **生成端趋同无法根治** | 探索集中在少数模板 | **诚实承认**（[[diverse-generation-prompts]] 实证）：生成端手段不充分，最终靠 因子评测阶段 增量 IC 兜底；方向索引监控覆盖率 |
| **LLM 幻觉（编造表名/字段名）** | 代码不可执行 | 数据引用检查器对照 JYDB 字典验证；禁止 LLM 臆造 |
| **过拟合** | 入库因子 OOS 失效 | 子期稳健性；规模分层；LLM 定性过拟合评估（[[llm-overfitting-risk-assessment]]，T=0.1）+ IS/OOS 衰减比交叉印证 |
| **LLM 过拟合评估自我确认偏差** | 定性评分虚高 | 该维度仅占 1/5 权重；须与量化衰减比交叉验证，不单独作拒绝依据 |
| **经验库过度过滤** | 错失非共识创新 | 定期注入新论文/思路重新激活冻结方向；保留"探索模式"不应用全部约束 |
| **经验库污染** | 低质量经验误导后续 | 三层过滤；使用次数追踪；过期/无效标记 deprecated |
| **LLM 成本不可控** | 大规模挖掘成本过高 | 宏微观分离将 LLM 调用压缩到每次 1-3 次；大部分计算在本地。注意反思式规划增加约 2 次/假设调用，须权衡 |
| **评测噪声** | 回测 IC 波动大 | 长评测区间（>5 年）；ICIR 优先于单点 IC；滚动窗口交叉验证 |

## 十一、关键设计决策与依据

| 决策 | 选择 | 依据 | 替代方案（已排除） |
|------|------|------|-------------------|
| 因子表示 | **程序级**（Python 代码） | [[expression-space-vs-code-space]]：代码空间可承载条件逻辑/状态切换等表达式树无法编码的构造 | 表达式级（RPN Token）：算子空间受限 |
| LLM 角色 | **宏观逻辑设计** + 结果解读 | [[macro-micro-co-evolution]] 分离原则：LLM 做少次高质量逻辑推理，本地做大量参数搜索 | LLM 全权负责参数选择：速度慢、成本高 |
| 评测标准 | **诊断框架** + 多维评分双轨 | [[standardized-research-reporting]] 提供审计视角，[[multi-dimensional-alpha-evaluation]] 提供筛选效率 | 单一 IC 最大化：忽略稳定性和过拟合 |
| **多样性判据** | **组合增量 IC**（硬）+ 相关性折价评分（软） | [[mutual-ic-vs-synergy-gap]]：互 IC 阈值数学上不成立；[[dual-residual-incremental-ic]] 提供正确检验 | **互 IC < 0.7 硬门槛（v0 方案，已排除）**：误杀协同因子、放行冗余 |
| 知识积累 | **双轨制**（成功经验 + 失败轨迹） | [[experience-library]] 提供组件复用，[[chain-of-experience]] 提供过程学习，两者正交互补 | 仅保留成功经验：丢失失败教训 |
| 防泄漏 | LLM **仅接触 Schema** | [[rd-agent-quant]] 的数据中心化设计 | LLM 直接分析行情数据：严重前瞻偏差 |
| 入库决策 | **三态**（Accept/Refine/Reject）+ 定向精炼 | [[dimension-targeted-refinement]]：精炼定向到薄弱维度，比盲目改进高效 | 二态（Pass/Fail）：丢失精炼路径 |
| 假设规划 | **反思式**（起草-批判-精炼） | [[reflection-based-planning]]：显式批判降低过早承诺错误逻辑；QRAFTI 消融 Sim@1 0.74→0.99 | 单次生成即执行：错误逻辑无中间拦截 |
| 参数搜索 | **贝叶斯优化**（TPE） | 比网格搜索效率高 10-100 倍，适合因子超参数的高维连续空间 | 网格搜索：维度灾难；手动调参：不可复现 |

## 十二、附录

### A. 与现有框架的关系定位

| 框架 | 本方案与其关系 |
|------|---------------|
| **AlphaGen / AlphaForge** | 本方案采用 LLM 驱动的代码空间搜索，表达能力更强；暂不实现 RL 驱动的集合优化。但采纳了 AlphaGen 的核心洞见——以组合增量 IC 取代互 IC 过滤（[[mutual-ic-vs-synergy-gap]]） |
| **CogAlpha** | 借鉴其四智能体质量检查器、防泄漏检测和多样化提示词，简化为三阶段流水线而非七级架构，降低复杂度 |
| **FactorEngine** | 借鉴程序级演化、宏微观分离和经验链，当前侧重单轮闭环，待稳定后引入多代演化 |
| **RD-Agent(Q)** | 核心架构参照五单元闭环，当前使用三阶段简化版；待基础稳定后引入多臂老虎机调度器 |
| **LLM-MCTS**（Shi, Duan, Li 2025） | 借鉴五维评分、维度定向精炼、频繁结构规避、LLM 过拟合评估。当前**不实现 MCTS 树搜索**（搜索预算为脱离 MCTS 的简化版），待稳定后引入完整树搜索控制层 |
| **东吴金工 Factor Iteration Skill** | 借鉴 Agent-Script 分工和工具沉淀，尤其是"Agent 负责思路、脚本负责执行"的模式 |
| **QRAFTI** | 借鉴四部分诊断报告、计算图追溯和反思式三阶段规划 |

### B. 后续迭代方向

1. **引入 MCTS 树搜索**：将 3.4 的简化预算分配升级为 [[mcts-in-factor-mining]] 的完整 UCT + virtual expansion，回归 [[dynamic-search-budget-allocation]] 的 breakthrough 触发机制
2. **多代演化**：引入 FactorEngine 式的程序级跨代演化（因子思维进化），实现因子的多轮精炼
3. **因子组合优化**：参照 AlphaForge 的动态权重组合（[[dynamic-factor-combination]]），将多个精英因子（含协同型因子）合成为 Mega-Alpha
4. **多臂老虎机调度器**：参照 RD-Agent(Q)（[[factor-model-co-optimization]]），在因子精炼和全新探索之间自适应分配算力
5. **高频因子挖掘**：扩展至分钟级数据（[[high-frequency-factor-mining]]），探索日内微观结构因子
6. **多市场扩展**：从 A 股扩展至港股、美股，验证因子的跨市场泛化能力
7. **基本面深度挖掘**：参照 [[ai-fundamental-factor-mining]]，引入财务数据的深度语义理解
